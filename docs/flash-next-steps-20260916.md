# 去重后的下一步 Flash 优化建议

## 结论

当前固件 **52,412 / 57,344 B**，余量 **4,932 B**。下一步建议做“**两类记录的专用内置日志原型**”，与当前 FDS 实现进行整包对比；以净节省至少 **1 KiB** 作为建议的采用门槛。这个门槛是投入产出判断，不是已经测出的收益。

如果后续功能已明确需要多出约 8 KiB 应用容量，应直接设计配置和标注外置迁移，避免先完成一次内置格式迁移，随后又迁到外置。当前没有这样的新增功能预算，所以优先评估保持分区不变的方案。

本次重新分析了最终 ELF 和存储源码，没有修改生产固件。

## 1. 当前占用与真正可优化的边界

| 模块组合 | 当前归属 Flash | 判断 |
| --- | ---: | --- |
| main、EPD 服务、命令/显示队列 | 14,805 B | 包含启动和跨模块内联；大函数不等于大块重复，继续零散去重难以保证明显收益 |
| GUI 布局、GFX、u8g2 | 10,347 B | 已固定屏幕、颜色路径和字体方向，已合并日期输出；保留整帧和局刷行为 |
| 字库管理、传输和字体几何辅助 | 5,464 B | 字模已在外置；剩下主要是执行代码、校验与事务控制 |
| FDS、fstorage 和后端 | 3,518 B | 两种应用记录使用了通用存储状态机，最值得做结构性替换的原型 |
| GPIOTE 驱动 | 1,220 B | 当前用于单个可配置引脚恢复广播；可另评估专用唤醒实现，但需要实机验证 |

统计由 `output/flash-next-20260916/analyze.py` 针对去重后的 `final-build/nrf52811_xxaa.out` 生成，完整归属见同目录 `sources.json` / `symbols.json`。各模块归属会随 LTO 内联位置变化，不能用表中某一行的变化代表该模块改动的收益；准确收益仍应通过同配置 A/B BIN 比较。

## 2. 首选原型：只管理配置与标注

### 已核实的需求

- 配置结构 `epd_config_t` 为 **14 B**，当前 FDS 按 **16 B** 对齐保存。
- 日历标注为 **16 B 头 + 最多 64 × 16 B 记录 = 1,040 B**。
- 应用没有其他 FDS 记录使用方；配置、标注和共享 GC 共注册三个回调。
- 内置存储区仍为 `[0x27000, 0x29000)`，共两页、8 KiB。
- 当前 FDS 的读写 CRC 开关已经关闭；没有再次关闭 CRC 的节省。新日志的 CRC 需要计入实现成本。

### 原型边界

1. 保留现有配置/标注对外接口和异步完成语义，存储后端集中串行处理两种记录。
2. 保留 `nrf_fstorage_sd`，通过 SoftDevice 支持的异步接口写内置 Flash。
3. 在原来两页内采用追加记录：类型、版本、长度、序号、CRC，最后写入提交标志。
4. 换页时复制两种最新有效记录，确认新页有效后再回收旧页；删除配置也需要可恢复的删除记录。
5. 配置继续使用不可变快照；标注继续锁住正在保存的数据，避免为新日志再增加一个 1,040 B 常驻副本。
6. 配置高频更新不应每次都重写整份标注；仅在换页时复制仍有效的数据。

这是代码体积优化，**不会释放原来的 8 KiB 数据分区**。FDS 本身至少需要一个数据页和一个交换页，不能简单改成一页；项目 SDK 的编译检查也明确禁止少于两页。[Nordic FDS 配置说明](https://docs.nordicsemi.com/r/bundle/sdk_nrf5_v16.0.0/page/group_fds_config.html?contentId=Jz6PRaujHpgLaBt6helqug)。

### 收益如何计算

当前直接归属 FDS 的代码约 **2,400 B**，其余 fstorage/后端约 **1,118 B**。继续写内置 Flash 时，不能把后端也计为可全部删除的收益。

`净节省 = 移除的 FDS/旧适配代码 − 新日志/新适配/旧格式迁移代码`

建议原型验收：

- 净减少至少 **1,024 B**，即最终 BIN 不超过 **51,388 B**；此时余量至少 **5,956 B**。
- 与当前业务兼容，静态 RAM 不出现新的千字节副本。
- 通过逐次写入/擦除中断恢复、换页、序号回绕、截断/损坏记录测试。
- 通过 BLE 活跃期间异步写入、连续配置覆盖、标注保存/清除交错、保存失败后重试和删除成功后才复位的测试。

如果只能省两三百字节，建议保留现有成熟实现，避免用新存储格式的维护成本换取有限空间。

### 旧 FDS 迁移是必须单独计算的成本

不能删除 FDS 后假设旧设备数据自然可读，也不能在新日志提交前擦掉唯一有效副本。

原型先测“新格式正常运行”的大小，再评估包含旧 FDS 读取/迁移路径的升级版本。需要覆盖旧 FDS 正常页、交换页、GC 中断和部分写入状态，并明确新格式识别后不再运行 FDS 初始化。

如果为迁移一直保留完整 FDS，结构性节省很可能被抵消。可研究小型只读迁移器或受控过渡版本，但都要单独证明恢复能力和版本路径；不能把迁移结束后的理想体积冒充所有旧设备可直接升级的镜像体积。

## 3. 其他候选的优先级

### 次选：单引脚唤醒替代通用 GPIOTE 路径

当前 `main.c` 只在非图片模式广播超时后，为一个 `wakeup_pin` 配置低功耗上升沿检测；触发后关闭检测并恢复广播。通用 GPIOTE 驱动占 1,220 B，是一个有边界的专用化候选。

需要保留“引脚已为高电平时如何设防”、重复设防、低到高变化、广播恢复及 System OFF 唤醒的区别，不能直接换成周期轮询。净收益尚未测量，新实现也有代码成本；必须验证实际引脚电平、功耗和中断行为，所以当前排在存储原型之后。

### 顺带审计：开发板兼容宏

构建仍定义 `DEVELOP_IN_NRF52840`，为在 nRF52840 开发板上开发 nRF52811 固件启用 NFC 引脚配置逻辑。若产品还要支持该开发板就应保留；如果确认只运行真实 nRF52811，可独立 A/B。没有实测节省量，不将其算作千字节级候选，也不删除芯片勘误处理。

### 暂不优先

- **继续广泛拆函数/强制 noinline：** 上轮实测收益不稳定；已有去重共省 304 B。
- **缩小 FDS 队列或回调表：** 主要影响 RAM；当前三处回调注册还必须保留足够容量。
- **删 FST2 或旧图片协议：** 有存量设备/客户端兼容代价，先有停止支持的依据再评估。
- **搬出日历小表：** 约千字节毛量还要抵消读取、格式和错误恢复代码，更适合为了资源可更新性实施。
- **裁剪农历范围、校验或恢复分支：** 会改变业务或可靠性，不能视作等价优化。

## 4. 何时改走外置迁移

如果新增功能预算超过当前 4,932 B，且专用日志也不能满足，再将配置与标注一起迁到外置 Flash，并同步处理字体分区、启动顺序、工具、实际 Bootloader 的 DFU 上限和回退兼容性。

完成整个布局升级后应用分区才有机会从 56 KiB 扩为 64 KiB。以当前代码大小不变计算，余量为 **65,536 − 52,412 = 13,124 B**；实际还需计入新增代码和删除代码，不能将这个条件值当作迁移后的测量值。

详细分区约束见[外置迁移路线](flash-optimization-roadmap-20260915.md)。本轮建议的下一项交付是：**独立存储原型 + 体积 A/B + 掉电恢复测试 + 旧格式迁移成本评估**，通过门槛后再替换正式存储实现。
