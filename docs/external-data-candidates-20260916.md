# 当前数据外迁清单（2026-09-16）

## 结论

当前应用为 **52,412 B**，内置应用区余量 **4,932 B**。可优先外迁的数据分为两组，收益不能混算：

1. **配置 + 日历标注的持久化副本**：两者全部迁出，处理 Bootloader/链接布局后，有机会回收内置 **8 KiB 数据分区**。这是容量收益最大的方向。
2. **日历资源表**：当前最终 ELF 中合计 **1,114 B**，可以做成可更新资源包；这是常量毛量，读取、校验、缓存及缺失处理代码会抵消部分收益，净节省尚未实测。

字体字模已经外置。GUI、字体解码、蓝牙、面板驱动的大部分占用属于执行代码，不能作为“数据外迁”收益。

## 1. 模块清单

| 数据 | 当前存放位置及规模 | 是否值得迁移 | 收益口径 |
| --- | --- | --- | --- |
| EPD 配置：引脚、型号、模式、周起始日、全刷周期 | 内置 FDS；结构 14 B，记录载荷按 16 B 对齐 | **优先，与标注一起迁** | 减少对 FDS 的依赖；单迁这 14 B 不能释放整个内置数据区 |
| 用户日历标注：日期、标签、颜色、位置 | 内置 FDS；最多 1,040 B；另有 RAM 活动副本 | **优先，与配置一起迁** | 全部持久化数据迁走后才具备回收 8 KiB 分区的条件；RAM 副本仍保留 |
| 公历/农历节日日期与名称 | 应用常量表；180 + 132 = 312 B | 适合资源包 | 减少常量、支持资源独立更新；特殊节日计算仍是代码 |
| 放假、调休表 | 应用常量表；78 B，当前对应 `HOLIDAY_YEAR=2026` | 很适合按年更新 | 当前空间收益小，主要价值是以后不用为换年重新编译固件 |
| 农历月份、日期、星期、干支、生肖、节气名称 | 应用常量表；648 B | 可随日历包一起迁 | 是当前日历包中最大的常量部分，需要从 SPI 读入缓冲后输出文字 |
| 农历年份与节气计算表 | 应用常量表；76 B | 适合扩展年份时迁移 | 当前很小；已有显示范围 2025–2027，另留 2024 数据处理春节前日期 |
| 三套字体字模 | 外置 FM25Q04B；仓库对应文件共 9,534 B | **已完成** | 当前内部 ELF 不含这些字模，不能再次计算节省 |
| 七段数字映射、几何参数 | 内置；10 + 35 = 45 B | 不优先 | 数据少，外读和缓冲开销可能超过收益 |
| 字体缺失时的占位几何参数 | 内置；最终 ELF 两份共 54 B | 建议保留 | 外置资源失效时仍要能显示占位内容 |
| UC8179 波形/初始化数据 | 已使用短模板生成 LUT，其他主要为代码中的常量 | 不优先 | 当前不是几百字节独立 LUT 数组；外迁增加面板初始化的资源依赖 |
| 新增图片、图标、开机画面 | 当前未发现可外迁的内置整帧位图 | 后续新增时优先外置 | 避免应用增长，不能算作当前已有收益；800×480 单色原始位图为 48,000 B |

配置和标注位于应用之外的 FDS 数据分区，所以不能从 52,412 B 应用镜像中直接减去 14 + 1,040 B。

## 2. 日历资源的精确拆分

以下字节数来自当前最终 ELF 的实际对象，非旧导出包大小：

| 符号/内容 | 字节 |
| --- | ---: |
| `Lunar_DateString`，农历日名 | 217 |
| `Lunar_MonthString`，月名 | 91 |
| `Lunar_MonthLeapString`，闰月标记 | 8 |
| `Lunar_DayString`，星期 | 28 |
| `Lunar_StemStrig`，天干 | 40 |
| `Lunar_BranchStrig`，地支 | 48 |
| `Lunar_ZodiacString`，生肖 | 48 |
| `JieQiStr`，节气名称 | 168 |
| 上述文字合计 | **648** |
| `festivals` / `festivals_lunar` | **312** |
| `holidays` | **78** |
| `lunar_month_days` / `solar_1_1` | 20 + 20 |
| `YearMonthBit` / 节气基准 `days` | 12 + 24 |
| **总计** | **1,114** |

此前路线文档的 1,090 B 未包含 24 B 节气基准表；这里将其纳入完整日历包候选。时间换算用的固定公历规则小表暂留内置，不为节省几十字节引入额外 SPI 读取。

外迁后的净镜像收益必须按 `删除的常量和旧读取逻辑 − 新读取/校验/错误处理逻辑` 实测，不能承诺省满 1,114 B。若为了外置损坏时完整显示，又在固件中保留全部原表，则失去这部分常量节省。

## 3. 仓库已有导出文件，但没有完成日历外置

`tools/dist/` 下已有月份/日期/节日等 `.bin`，另有 `lunar_db.bin`、`ui_bundle.bin` 和 `manifest.json`。本次逐字节核对了 15 项候选数据：11 项与当前 ELF 相同，4 项不同：

| 文件 | 当前 ELF | 现有 dist 文件 |
| --- | ---: | ---: |
| `lunar_month_days.bin` | 20 B | 28 B |
| `lunar_solar_1_1.bin` | 20 B | 28 B |
| `lunar_jieqi_year_bits.bin` | 12 B | 18 B |
| `holiday_adjustments.bin` | 78 B | 82 B |

比对记录：`output/external-data-20260916/candidate-data.json`。

`manifest.json` 为 **EPDR v1**，当前字体存储实现使用 **FST3**（兼容旧 FST2），只管理三个字体槽。当前生产代码没有加载这些日历导出资源的路径。`lunar_db.bin` 的 5,833 B、`ui_bundle.bin` 的 1,029 B 不能算成当前应用可删除的数据。

因此现有导出文件可以作为资源格式工作的参考，但应依据当前源码重新生成、检查版本/年份和 CRC，不能按 EPDR 中的旧偏移直接写入当前设备。

## 4. 外置空间应先划分

当前 FM25Q04B 为 512 KiB，FST3 主目录位于首扇区，备份目录位于末扇区，中间 504 KiB 全部属于字体更新分配器。即使字模本体较小，也不能把未使用地址当成已经保留的空间；安装在设备上的字体位置和大小仍需读取确认。

若同时迁出配置/标注和日历资源，可评估以下布局，地址末端不包含在区间内：

| 分区 | 地址 | 容量 |
| --- | --- | ---: |
| 字体主目录 | `0x00000–0x01000` | 4 KiB |
| 字体数据与更新空间 | `0x01000–0x7B000` | 488 KiB |
| 日历资源 A | `0x7B000–0x7C000` | 4 KiB |
| 日历资源 B | `0x7C000–0x7D000` | 4 KiB |
| 配置/标注日志 A | `0x7D000–0x7E000` | 4 KiB |
| 配置/标注日志 B | `0x7E000–0x7F000` | 4 KiB |
| 字体备份目录 | `0x7F000–0x80000` | 4 KiB |

这是候选布局，尚未实施。日历双副本用于更新失败后保留旧包，当前 1,114 B 数据加包头可放入一份 4 KiB；如果要扩展很多年的放假表，需要重新预算。

只迁配置/标注时可暂不划分日历 A/B，字体区保留 496 KiB。迁移前必须检查新分区是否被旧 FST2/FST3 有效记录占用，先搬移并确认目录提交，再使用新分区。

需要同步更新字体分配器、`tools/font_store_tool.py`、`html/js/font_store.js` 及容量/布局能力报告；旧固件的分配器可能覆盖新区，回退版本也必须理解新布局。

## 5. 实现顺序与取舍

### 如果目标是扩大应用容量

1. 建立外置分区和统一访问协调，复用现有 FM25Q04B 驱动；按页编程、按扇区擦除，保留等待和喂狗。
2. 在当前 56 KiB 范围内实现配置 + 标注迁移。采用序号、CRC、最后提交标志和双页回收，先确认外置副本有效，再退休旧数据。
3. 保留配置的 RAM 副本和标注的 1,040 B 活动缓冲，维持 BLE 接收、回读、刷新和保存锁定语义。
4. 启动时先确保外置存储可读，再装载配置；当前字体探测已在服务初始化之前，但仍需独立处理失败、默认配置和 BLE 恢复入口。
5. 核实并升级实际 Bootloader 的 DFU 应用上限，再调整应用链接区，完成后才可复用内置 8 KiB。

按当前代码大小不变计算，64 KiB 应用区余量为 **13,124 B**；最终值还需计入新旧代码差额。

### 如果目标是日历独立更新

先做日历资源包原型。包头应包含格式版本、有效年份、记录长度/数量和 CRC；界面通过有边界的读取函数取记录/字符串，不能将 SPI 地址当普通 C 指针。

分页绘制会多次调用日历逻辑，建议按帧/月缓存查询结果，或用小缓冲按记录读取，避免在逐像素路径反复访问 SPI。整包复制到 RAM 简单，但要另付约 1.1 KiB 缓存成本；本轮没有为此承诺 RAM 节省。

资源缺失时保留基本公历/时钟与资源修复入口；扩展年份需要同步修改当前年份边界和越界处理。增加新的中文名称还要确保已安装字体包含对应字形。

### 不作为本次数据外迁对象

- 绘图页缓冲、OLD/NEW 局刷缓冲、BLE 队列和活动状态：需要频繁随机读写，继续保留 RAM。
- C 函数、驱动函数表、SDK 观察者表、启动中断向量：属于执行和注册机制，不能通过移动数据保持原用法。
- nRF52811 不支持从当前 SPI Flash 直接执行代码；执行代码外置不是本次数据资源方案。[Nordic 对 nRF52811 XIP 的官方说明](https://devzone.nordicsemi.com/f/nordic-q-a/48713/nrf52811-supports-xip-execution-in-place-feature)。

**推荐优先级：配置与标注一起外迁用于扩容；日历资源包用于独立更新。字体保持现有外置方案，微小常量暂留内置。** 本次仅分析，没有改动固件或设备存储。
