# 离线时钟漂移分析与修复

实测现象：同步后离线运行约 7 天，设备时间比标准时间慢约 3 分钟。

## 原因与误差量级

当前主线使用 nRF52811 的内部低频 RC（`NRF_SDH_CLOCK_LF_SRC=0`）。
SoftDevice 配置每 4 秒检查温度、最迟每 8 秒校准一次，符合 SDK 的建议；
断开蓝牙和停止广播没有关闭 SoftDevice，因此离线仍有硬件校准。
RC 校准后的规格为 ±500 ppm，折算约 ±43.2 秒/天，7 天慢 180 秒约为
−297.62 ppm，与此范围吻合。这个量级支持 RC 频偏是主要原因，仍需实机复测确认。

`NRF_SDH_CLOCK_LF_ACCURACY=1` 是向 BLE 协议栈声明 500 ppm 的精度等级，
改成 20 ppm 不会提高 RC 实际精度。依据：仓库 SDK 的
`components/softdevice/s112/headers/nrf_sdm.h` 中 `nrf_clock_lf_cfg_t` 注释及
[Nordic nRF52811 产品规格书](https://docs-be.nordicsemi.com/bundle/nRF52811-PS/raw/resource/enus/nRF52811_PS_v1.1.pdf?save_local=true)。

另核实了以下区别：实际编译的是 `app_timer2.c`，重复定时器沿上次截止时间推进，
并补调到期回调；回调在 RTC 中断执行。因此不能把普通刷屏忙等或普通回调迟到
直接认定为每秒都累计的软件丢秒。当前预分频为 1，`APP_TIMER_TICKS(1000)`
恰好为 16384 ticks，没有一秒定时周期的整数舍入误差。

## 本次实现

- `main.c` 改为累计 24 位 RTC 的 tick 差值，保留不足一秒的余量，短临界区保护
  时间状态；延迟回调和重复补调不会凭回调次数增减时间。默认 RTC 每 1024 秒回绕，
  由持续运行的 1 Hz 定时器保证采样间隔小于一次回绕；不支持停机调试跨越整个回绕周期。
- 校时只设置墙上时间及其秒内相位，不停启定时器，也不重置单调运行时间的余量。
  SDK 保留原始 `APP_TIMER_KEEPS_RTC_ACTIVE=0`。应用的 1 Hz 重复定时器一直有效，
  `app_timer2` 不会进入“没有有效定时器才停止 RTC”的分支，因此无需修改 SDK。
- 按实测配置 `APP_CLOCK_CALIBRATION_PPM=-298`，用
  `corrected_ticks = raw_ticks × 1000000 / (1000000 + ppm)` 补快，
  整数除法余量持续保留。仅针对当前 RC 板配置，不包含外部晶振分支；
  所有补偿值共用一套计算，设为 0 时输出原始 tick，无需额外条件编译。
- 显示刷新按分钟/日/维护周期的跨越补刷，避免补偿或延迟采样跳过整边界后漏刷。
- 网页自动校时和切换模式时，在真正执行 GATT 写入前生成时间，减少网页排队导致的
  初始偏慢。BLE 传输、固件命令排队和秒级时间载荷仍可能带来初始误差。

## 调整与复测

GCC 和 Keil 共用 `main.c` 中的补偿宏；SDK 目录保持原样。
保留当前 RC 默认 −298 ppm 补偿。调整时直接修改这个源码宏：

```c
#define APP_CLOCK_CALIBRATION_PPM (-298) /* 设为 0 可关闭补偿 */
```

不再提供 Makefile 补偿参数入口，也不按时钟源自动选择补偿值；两种工具链都读取同一份源码配置。
不要只在 `main.c` 内覆盖
`APP_TIMER_KEEPS_RTC_ACTIVE`：SDK 的 `app_timer2.c` 是单独编译的，不会看到这个局部定义。
本次不需要覆盖此 SDK 参数，也不需要修改 RTC 预分频或 IRQ 优先级。

其他未测量的板子应先设为 0；此数值针对本次报告的设备。
允许范围为 −2000 至 +2000 ppm。正值表示振荡器快，需要减慢；负值表示振荡器慢，需要加快。
首次测量使用 `ppm = (设备经过秒数 / 标准经过秒数 - 1) × 1000000`。
如果已启用补偿，重测后应更新为
`new_ppm = (1000000 + old_ppm) × (设备经过秒数 / 标准经过秒数) - 1000000`，
避免把剩余偏差误当成总频偏。

刷入后重新同步，记下同步后的初始偏差，在相近温度条件下离线运行 24 小时及 7 天，
比较偏差的增量。以本次近似测量计算，补偿约增加 25.75 秒/天；数学模拟可以验证
补偿公式和方向，无法保证 RC 在不同温度、电压、个体上的长期精度。

## 软件流程中是否阻塞 RTC

本次结论来自源码与主机模拟，尚未测量实机中断延迟。应区分硬件停止计数、
中断延迟、主循环等待及屏幕滞后这四种情况。

| 路径 | 代码行为 | 对计时的影响 |
| --- | --- | --- |
| 主循环空闲 | `idle_state_handle()` 调用 `nrf_pwr_mgmt_run()` / `sd_app_evt_wait()` | System ON 等待事件，RTC 继续计数 |
| 刷屏 BUSY 等待 | `EPD_WaitBusy()` 在主循环中轮询并喂狗，未关中断 | 显示及命令处理可能滞后，RTC 继续计数 |
| 外部 Flash 擦写 | `fm25q04b_wait_ready()` 轮询 WIP，未关中断 | 当前上下文被阻塞，RTC 继续计数 |
| 短临界区 | 时间状态、队列和配置的有限复制，部分 BLE 通知调用 | 应用中断短暂推迟，硬件 RTC 继续计数 |
| 1 Hz 回调 | 先按真实 tick 累计时间，再投递刷新请求；不直接刷屏或访问 SPI Flash | 回调迟到由累计差值补计 |
| SDK 空闲停表 | 仅所有定时器都无效且 `APP_TIMER_KEEPS_RTC_ACTIVE=0` 时执行 STOP | 永久有效的时钟定时器避免此分支 |
| SYSTEMOFF / 复位 | 显式睡眠、极低电量、图片模式超时关机或 DFU 等路径 | 时基停止或状态丢失，唤醒/重启后需重新校时 |

应用未发现调用 `app_timer_pause()`、`app_timer_stop_all()` 或直接写 RTC STOP/CLEAR、
LFCLKSTOP 的正常时钟路径。当前计时不调用 `app_timer_stop(m_clock_timer_id)`；
旧版校时停启定时器的做法已移除。`app_timer2` 以旧截止点加周期追赶到期事件，
不能把普通刷屏等待认定为每秒累积的软件丢秒。

仍有一条中断长路径需要注意：`WRITE_BLOCK` 是绕过小控制队列的当前 CRC 传图命令，
BLE 写事件会直接调用 `cmd_write_block()`。若面板尚未打开，或第一块需要从时钟模式
切换为图片模式，它可能执行 `epd_ensure_display()` 及 `epd_switch_from_clock_mode()`。
UC8179 单次初始化包括 30 ms 复位和名义 1000 ms 的 BUSY 超时，可能发生两次初始化。
这段工作可能在 BLE 事件中断中持续约 1–2 秒；若其优先级不低于 RTC 中断，会推迟
RTC 回调，但不会停止 RTC 硬件计数，当前差值累计会补计时间。
后续若要消除这类中断长处理，应把首块初始化交给主循环，并配套 READY/重试和数据缓存；
不能直接把完整传图包塞进当前最大 16 字节的控制队列。本次不改图传协议。

另发现 BUSY 超时使用 `16384 / 1000 = 16` 的整数截断，名义 30 秒的计数预算实际
约为 29.296875 秒；`epd_elapsed_ms()` 的日志测时也有相同除数问题。这影响超时和
性能日志的准确度，不改变 RTC 频率，不能解释稳定的每周慢 3 分钟。本次保留原超时策略。

正常 1 Hz 采样间隔远小于 1024 秒回绕周期。若异常屏蔽应用中断且不读取时间超过
一个完整回绕周期，当前 24 位差值无法还原少掉的整圈；SPI/日志的异常无界等待也
可能导致卡死或看门狗复位。源码审查不能替代这些故障的实机注入和测量。
