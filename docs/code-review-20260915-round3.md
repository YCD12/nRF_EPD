# 第三轮审查：稳定性与内置 Flash 优先优化

后续实施结果见 [第三轮修复与优化记录](code-optimization-20260915-round3.md)。下文保留审查时 `0x31` 的发现与实验基线，不代表修复后的 `0x32` 状态。

审查对象为设备报告版本 `0x31` 的当前工作区。复核结论：正常路径的回归通过，但仍存在可复现的异步竞态、传图取消状态遗漏，以及上一轮字体裁剪带来的缺字显示回归，不能仅凭测试通过就判断可稳定发布。内置 Flash 还有优化空间，暂不需要为节省几百字节迁移外置资源。

本次只新增审查报告，实验和复现位于 `output/review3/`；业务源码、暂存区与上一轮发布包保持本次审查开始时的状态。实验镜像不是发布固件。

## 一、稳定性问题

### 1. P1：标注回读存在 TX complete 唤醒丢失

位置：`EPD/calendar_annotations_tx.c:43`、`:51`、`:54`；`EPD/EPD_service.c:1554`。

发送状态机先调用 `send()`，再设置 `waiting_tx = true`。当前 SoftDevice 事件在中断上下文分发（`NRF_SDH_DISPATCH_MODEL=0`）。如果 TX complete 在发送调用返回到设置等待标志之间发生，中断中的 wake 会先清掉等待位，随后主循环又把它设回 true。没有下一次通知完成事件时，回读停住；`annotations_tx.active` 还会持续阻止标注修改。

最小复现直接编译当前发送模块，在 send 回调返回前调用真实 wake：16 字节空标注、8 字节通知包，反复 process 后仍为 `active=1 waiting=1 offset=3 send_calls=1`。

建议借鉴字体模块的发送顺序：先登记等待，再调用发送接口；成功时只推进该次发送对应的偏移。GET 重启、断开取消也必须通过 request 标志或任务代次与 worker 串行交接，避免旧发送结果修改新任务。单独使用 `volatile` 不能解决这些操作顺序问题。

### 2. P1：传图准备后断开会让时钟停止更新，并可能留下 GPIO 引用

位置：`EPD/EPD_service.c:1195`、`:563`、`:644`；`EPD/epd_refresh_policy.h:49`。

`RESET_TRANSFER` 在首块图片到来前就设置 `transfer_active=true`。若此后断开，disconnect 没有清除图片会话，也没有图片会话超时恢复。刷新策略只要看到 transfer_active 就拒绝刷新，包括强制刷新，因此仍处于时钟模式的设备可能一直停留在旧时间。

如果 RESET_TRANSFER 在 GUI 刷新中到达，`finish_refresh` 的 must_yield 分支直接返回，绕过第 605 行的 `EPD_GPIO_Uninit()`。此前第 448 行取得的刷新引用没有交还；disconnect 只释放连接自己的引用。

从当前源码提取 RESET_TRANSFER 和 finish 分支、使用真实刷新策略的最小模型结果：`refs=1 transfer_active=1 forced_refresh=0`。这是源码控制流复现，尚未测量实板电流。

建议给图片会话增加主循环取消／超时收尾；保留需要的已显示图像状态，但释放“正在接收”的占用。刷新资源必须在所有退出路径对称释放；若要转交给图片任务，应明确转交所有权，而不是保留一个无归属引用。GPIO 初始化／关闭本身也应由主循环统一管理，避免中断穿插硬件初始化过程。

### 3. P1：INIT 仍可在刷新过程中重入操作面板

位置：`EPD/epd_cmd_policy.h:13`、`EPD/EPD_service.c:854`、`:1382`。

WRITE_BLOCK 已检查 is_refreshing，但同属立即执行命令的 INIT 没有相同保护。连接初始化或重新初始化刚好遇到 GUI 刷新时，BLE 中断可以调用 `epd_init()` 重设面板；主循环随后继续旧一轮写入／刷新流程。引用计数只能保护总线生命周期，不能保护面板命令序列。

该项由当前中断分发配置与调用路径确认，尚未做硬件故障注入。建议中断只记录 INIT 请求，并返回明确的忙／完成状态；显示 worker 在当前刷新安全结束或取消后执行。前端需等待真正初始化完成再传首块，不能只把 GATT write 完成当作面板已就绪。

### 4. P2：固定字体方向破坏了缺字占位图形

位置：`GUI/Adafruit_GFX.c:77`、`GUI/u8g2_font.c:74`。

`GFX_FIXED_FONT_DIRECTION_0=1` 时，底层 draw_hv_line 忽略 dir，全部画水平线。但缺字占位框仍通过这个回调请求两条方向 1 的竖线。因此正常字体显示通过，字体被删除、缺字或读失败时，占位框侧边消失并向右多画横线。

使用真实 GFX 与 u8g2 绘制同一个缺字：

| 配置 | 左侧边像素 | 错误伸出的顶部像素 | 缓冲哈希 |
| --- | ---: | ---: | --- |
| 通用配置 | 1 | 0 | `3d043319` |
| 当前固定配置 | 0 | 1 | `967a6166` |
| 实验修正固定配置 | 1 | 0 | `3d043319` |

只需在固定配置的回调中继续支持占位框所需的方向 1，不必恢复全部文字旋转。单独修正的 ARM 构建增加 16 字节 Flash。现有 placeholder 单测只统计回调次数，没有检查经过 GFX 后的最终像素，因而未捕获该回归。

### 5. P2：未使用引脚的 0xFF 哨兵仍传入 GPIO 配置接口

位置：`EPD/EPD_driver.c:169`、`:170`、`:171`。

初始化时会跳过可选的 BS／EN／LED 引脚，但释放时无条件调用 `pinMode(..., DEFAULT)`。未配置的值为 `0xFF`，SDK 的 nrf_gpio_cfg 使用它索引 PIN_CNF；其引脚断言不是业务层对未使用引脚的处理。可能触发断言或越界寄存器访问，不能依赖芯片忽略该访问。

建议在公共 GPIO 包装或可选引脚释放入口统一过滤 `0xFF`，并验证必选引脚范围。此项为源码确认，未在硬件上执行非法寄存器访问。

## 二、功能与维护边界

- **精确农历只到 2027 年。** `GUI/Lunar.h:17` 与 `GUI/Lunar.c:238` 明确将超出窗口的年份映射回 2025，节气也有同类处理。2028 年以后设备仍运行，却会显示错误的农历／节气。当前每年数据很小，优先在内置表扩展年份，不应为了几十字节继续缩短正确性范围。
- **当前 2026 放假数据正确。** 已核对元旦、春节、清明、劳动节、端午、中秋、国庆及调休；源码日期用十六进制编码，例如 `0x0613` 是 6 月 19 日。依据：[国务院办公厅 2026 年节假日安排，北京市政府转载](https://www.beijing.gov.cn/gate/big5/www.beijing.gov.cn/zhengce/zhengcefagui/202511/t20251104_4258873.html)。每年的假期表更新仍需明确入口。
- **标注回读表示 live 数据一致，不表示已经持久化成功。** `calendar_annotations_store_process()` 在重试耗尽后解除锁定，没有给前端返回落盘失败。需要独立的保存完成／失败状态，或在读取状态中区分 pending、persisted、failed。不能用重新读取 RAM 内容替代掉电恢复验证。
- **短小的可重试发送 worker 仍依赖主循环及时运行。** GUI 完整刷新长期占用 scheduler 时，收到的回读请求可能延后，而前端回读超时是 4 秒。后续可将刷新按页／阶段推进，让主循环在可安全暂停处处理任务；涉及共享 SPI 和面板顺序，不能直接在任意绘图回调里递归执行 scheduler。

更优的结构是：BLE 中断负责校验、复制和登记请求；图片／标注／字体各自拥有会话状态；单一显示执行者负责面板及 GPIO；存储执行者通过完成事件确认持久化。优先完成这些所有权边界，再考虑目录重命名。

## 三、内置 Flash 实测

使用仓库 ARM GCC 9.3.1、发布链接脚本、`-Os -flto`，每个实验使用独立源码副本和构建目录，SDK 不变。基线重新构建得到：

- text/data/bss：52,760 / 232 / 6,544 字节。
- 应用 Flash：**52,992 / 57,344 字节**，剩余 **4,352 字节**。
- 静态 RAM：6,776 字节；含保留的 2,048 字节栈后，剩余 6,832 字节。该余量不是最大栈使用量测量。

### 已有实测收益的低成本方案

| 独立实验 | 应用 Flash | 相对当前节省 | 代价与验证 |
| --- | ---: | ---: | --- |
| H/V 直线用单轴循环，减少通用 Bresenham 路径 | 52,848 | 144 字节 | 正常 GUI 与 OLD/NEW 对比通过；正式实现需明确零／负长度行为 |
| 两个字体初始化函数局部禁止内联 | 52,944 | 48 字节 | 保持行为；避免初始化代码扩张，收益依赖编译器 |
| LUT 按公共模板生成，替代三份 42 字节相似数组及指针映射 | 52,928 | 64 字节 | 使用 42 字节临时栈缓冲；六组 42 字节命令数据逐字节验证通过 |
| **合并以上三项** | **52,736** | **256 字节** | 静态 RAM 不变，Flash 余量 4,608 字节 |

组合实验通过正常 GUI 画面与时钟 OLD/NEW 对比。这个 256 字节是裁剪收益，**未包含本报告全部稳定性修复的成本**；不能把实验镜像当成已解决上述问题的最终固件。LUT 模板保留完整字节序列和喂狗，不删波形数据或等待步骤。

### 本轮测过但不优先的方案

| 实验 | 相对当前 Flash 变化 | 判断 |
| --- | ---: | --- |
| 全局 `-fno-inline-functions-called-once` | +16 字节 | 同时静态 RAM +8，未获益 |
| 单独禁止 u8g2_DrawGlyph 内联 | 0 | 无净收益 |
| 字体读接口仅保留外置读回调路径 | -16 字节 | 为很小收益增加产品条件分支，优先级低 |
| 字体缓存由 251 改为 256 | 0 | 没有 Flash 收益，还改变 SPI 读分块与栈结构 |

关闭调试符号、删除已经被宏排除的内置字模、删除未被链接的函数都不能减少实际烧录空间。CRC16 与 CRC32 不是可直接合并的同一种校验，不能为去重改变协议。

### 更大幅度优化：先评估专用内置持久化日志

当前实际存储类型只有配置和标注，可以在**仍使用内置 Flash** 的前提下，评估用专用双页追加日志替代 FDS 的通用记录管理：

1. 每条记录包含类型、长度、序号和 CRC，最后写提交标志；启动时只采用完整提交且 CRC 正确的最新记录。
2. 一个活动页加一个交换页。换页时复制两类最新记录，确认新页提交后再回收旧页；删除通过明确的空记录／墓碑表达。
3. 继续使用 SoftDevice 兼容的异步 Flash 后端，禁止写入源缓冲在完成前被覆盖。
4. 对每一次写入／擦除边界做掉电注入，并兼容旧 FDS 数据的迁移。

这条路线有机会减少通用 FDS 管理代码，比继续搬运几十字节常量更值得做隔离原型，但本轮未实现，**没有可承诺的净节省数字**。保留双页时，仍占用原来的 8 KiB 数据区；“减代码”和“释放数据分区”是两项不同收益。不能把 FDS 直接减为一个页来省空间。

若后续还不够，再对当前编译器版本、局部内联边界、图形裁剪和命令适配做有目标的 A/B 测量。停止兼容旧协议、移除 OTA、删除错误恢复都会改变产品能力，应作为明确的功能取舍单独评估。

## 四、外置 Flash：后备方案与实际收益

链接 map 中 `.rodata` 约 2.2 KB，包含 SDK 指针表、驱动表等，不能全部迁出。主要日历相关常量合计 **1,090 字节**：

| 候选数据 | 当前链接字节数 | 外置建议 |
| --- | ---: | --- |
| 农历两表＋节气年月位表 | 52 | 太小，当前留内置；扩展为长期可更新资源后再评估 |
| 当年放假调休表 | 78 | 外置的主要价值是按年更新，当前省 Flash 价值很低 |
| 公历／农历节日名称及日期记录 | 312 | 可合并到日历资源包，须有 RAM 文本缓存 |
| 农历月份、日期、生肖、干支、星期及节气文字 | 648 | 可外置，但会增加资源索引、读取与失败处理代码 |
| 局刷 LUT 三个数组 | 126 | 优先本轮内置模板生成；无需额外 SPI 依赖 |

这些字节数是可替代数据的毛量，不是净 Flash 节省。当前字体字模已在外置 Flash，nRF 固件里的字体解码器仍是执行代码；把更多字体文件放外置不会再次省下这部分代码。现有 FM25Q04B 路径是 SPI 数据读取，不能把任意 C 函数移过去后直接调用。

建议外置顺序：

1. **可更新日历资源包**：未来多年农历、节气和每年放假调休，统一版本、长度、CRC 和有效年份。加载时保留小的日期／文字缓存，避免每个绘图页重复读整个资源。当前表太小，优先为可更新性而做，不能承诺明显净节省。
2. **配置＋标注的持久化记录**：只有两者都迁出并完全移除 FDS，才有机会同时减少存储管理代码并释放当前 0x27000–0x29000 的 8 KiB 内置数据区。只迁标注、仍为配置保留 FDS，通常不能回收这两页。

第二条需要重新设计分区和迁移：过渡固件先在原应用大小限制内把旧数据复制到外置、校验并提交，再发布使用扩大应用区的固件。否则更大应用可能在首次启动迁移前就覆盖旧 FDS 数据。还需核实 bootloader 的应用数据保留配置和 DFU 可接受范围；仓库当前只提供 bootloader HEX，不能假设改应用链接脚本就足够。

FM25Q04B 为 512 KiB，字体 FST3 使用首末元数据扇区及中间循环数据区。其空白字节不等于可长期独占的空间；新增资源／存储区必须从字体分配器的容量范围中明确扣除，并同步前端打包工具、兼容迁移和掉电策略，防止后续字体更新擦掉新数据。

## 五、验证与推荐顺序

本轮重新运行全部主机回归：27 个 C 程序、13 个 Node 子测试、3 个 Python 测试通过；发布配置基线与 11 个独立变体的 ARM 构建完成。额外完成：TX 唤醒竞态复现、图片会话／引用控制流复现、真实 GFX 缺字像素对比、候选 GUI golden 对比和 LUT 命令字节对比。

复现与实验脚本：`output/review3/experiments.py`、`reproduce_tx.c`、`reproduce_placeholder.c`、`reproduce_lifecycle.py`；体积汇总 `sizes.json`，回归日志 `output/review3-host-tests.log`。测试未覆盖实际面板电流、射频中断时序、全路径栈峰值，未执行实机烧录。

建议按以下顺序处理：

1. 先修 TX 唤醒／重启竞争、图片会话取消及资源收尾、INIT 重入、缺字图形和无效 GPIO 引脚。
2. 合入已测量的三项内置优化，补零／负长度绘图测试，重新计算包含修复的最终 Flash 和栈预算。
3. 补持久化确认、扩展日历有效年份；必要时再做专用内置双页日志原型，用掉电测试和最终链接大小决定是否采用。
4. 只有内置方案达不到容量目标时，再引入外置日历包或完整持久化迁移。

目前能够确认的是：仍有 4,352 字节应用余量，且已有额外节省 256 字节的候选；**还没有到只能依靠外置 Flash 的阶段**。
