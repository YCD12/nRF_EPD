# Flash 优化优先级与外置迁移路线（2026-09-15）

## 结论

当前应用为 **52,716 / 57,344 B**，尚余 **4,628 B（约 4.52 KiB）**。可以继续优化，但字体外置、日志关闭、LTO、精简广播和格式化等主要低成本优化已完成。

建议先做有目标的代码去重；需要千字节级收益时，评估专用内置日志替代 FDS。需要明确扩大应用分区时，优先考虑将**配置和日历标注的持久化数据一起迁到外置 Flash**，配合移除 FDS 和升级布局，理论上可以回收内置 8 KiB 数据分区。

当前 nRF52811 没有 QSPI/XIP 能力，不能从 SPI NOR 直接执行程序。项目的 FM25Q04B 通过 SPI 命令读写，因此可迁的是资源和持久化数据；不能把 `GUI.c`、BLE 服务或字体解码器整个搬过去后照常调用。[Nordic 对 nRF52811 XIP 的官方答复](https://devzone.nordicsemi.com/f/nordic-q-a/48713/nrf52811-supports-xip-execution-in-place-feature)。

本次整理基于当前源码、最终 ELF 模块统计及前几轮实验，没有实施新的固件修改或迁移。下列模块体积是定位依据，未经新 A/B 验证的净节省不作承诺。

## 1. 内置 Flash 优化清单

| 优先级 | 模块及当前归属体积 | 可研究的优化 | 判断与验证重点 |
| --- | --- | --- | --- |
| P1 | 主程序、EPD 服务、命令/显示入口：15,147 B | 合并重复参数校验、响应封装和收尾；明确可共用的命令处理路径 | 体积最大，但包含跨模块内联；必须保留 INIT 排序、断连代次、队列背压和刷新取消行为。不能通过合并异步状态丢失语义 |
| P1 | GUI 布局 6,101 B + GFX 2,722 B + u8g2 1,460 B | 日期/文本布局复用、重复坐标与样式处理、低电量/提示页面的共用绘制 | 先找重复实现，再做同配置 A/B 和 GUI golden；已有固定屏幕/方向裁剪。上一轮局部 noinline 仅省 16–32 B，部分反而增大，不宜继续盲目加属性 |
| P1 | 字库管理/传输：5,498 B | 复用帧校验、ACK、错误处理；评估旧 FST2 兼容代码的生命周期 | 字模已外置，当前主要是执行代码。终止旧格式支持会影响存量资源；完整 CRC、提交顺序和断连恢复仍需保留 |
| P2 | SDK FDS/fstorage：3,518 B | 用专用双页追加日志保存配置和标注，替代通用 FDS 记录管理 | 千字节级候选。当前直接归属的 FDS 约 2,400 B，fstorage 及后端约 1,118 B；继续写内置 Flash 时后端仍需保留，新日志也有成本。最终收益需原型实测 |
| P2 | 启动与硬件兼容代码 | 核实固定 nRF52811 产品是否仍需要 `DEVELOP_IN_NRF52840` | 当前宏确实开启了一段开发板 NFC 引脚兼容代码。仅在确认不再运行于 nRF52840 开发板后评估关闭；不删除目标芯片勘误处理。本次未测节省量 |
| P3 | 农历/节气 1,560 B，另有 GUI 中节日表 | 按数据用途压缩、共享日期格式，或改为外置日历包 | 当前表较小；不要缩短正确年份范围。外置的主要价值是按年更新，不是马上省很多代码 |
| P3 | SDK BLE/DFU 2,764 B、定时器 2,000 B、硬件驱动 2,670 B | 逐项确认真实使用的能力和强制保留入口 | 精简广播已落地，不能再计一次收益。SPI、RTC、GPIO、WDT 都有实际调用；删除模块前必须证明功能不需要 |
| 低 | UC8179：1,670 B；时钟局刷：226 B | 少量公共命令/参数整理 | LUT 模板化已完成。不要为少量空间更改波形、等待、喂狗和 OLD/NEW 顺序 |

**不再列为待优化收益：** 删除调试信息、删除已被 LTO/垃圾回收去掉的函数、再次外置字模、缩小 BSS 缓冲或栈。这些不会直接减少当前应用镜像，或收益已包含在基线中。

### 专用内置日志的评估边界

保留活动页和交换页；记录包含类型、长度、序号、CRC、最后写入的提交标志。换页时保留配置和标注的最新有效记录，新页提交后才回收旧页。继续使用兼容 SoftDevice 的异步 Flash 后端，并保证写入源缓冲在完成前不被覆盖。

对擦写的各个边界做掉电恢复测试，验证旧 FDS 数据迁移、删除/恢复默认行为及多次更新。**这条路线减少的是管理代码，仍占用原来的 8 KiB 数据分区。** 不应直接把 FDS 页数减成一页。

## 2. 哪些内容适合迁到外置 Flash

| 内容 | 可行性 | 内置 Flash 收益与代价 |
| --- | --- | --- |
| 字体字模、图片、静态图标 | 可以；当前主要字模已外置 | 后续新增资源放外置可避免内置增长；已有字体没有第二次迁移收益 |
| 农历年份表、节气表、节日名称、放假调休表 | 可以，使用有版本/有效年份的资源包 | 当前主要候选数据毛量约 1,090 B，新索引、缓存、读取和失败处理会抵消部分收益。适合为了可更新性迁移 |
| 配置 + 日历标注的持久化副本 | **可以，是最值得评估的扩容方向** | 两者全部迁出并移除 FDS 后，有机会回收内置 8 KiB 分区；还可能减少管理代码，但净代码收益单独测量 |
| GUI 布局参数、绘制指令表 | 可将适合的数据部分迁出 | 需要保留解释/渲染引擎；原来由简单 C 表达的逻辑不保证改成资源后更小。当前不是现成可直接搬走的大 UI 资源包 |
| OTA 固件下载缓存 | 可作为独立 Bootloader 工程研究 | 解决下载暂存问题，不自动扩大最终执行的应用分区；当前应用仍必须装得进内置 Flash |
| GUI、u8g2、BLE、SPI 等 C 函数 | **不能直接外置执行** | nRF52811 无 XIP；当前启动链也没有外置代码加载器 |
| `m_epd`、绘图缓冲等活动 RAM | 不适合作为普通 RAM 搬移 | SPI NOR 需擦写，访问方式不同。迁出持久化副本也不等于可以删除其运行时 RAM 副本 |

日历数据毛量分解：文字 648 B、节日记录 312 B、放假调休 78 B、主要农历/节气位表 52 B。不要把整个农历模块的执行代码、GUI 日历绘制代码都算成可搬走的数据。

### 代码先存外置，再加载到 RAM 执行？

硬件层面可以研究，但不是当前工程可直接使用的能力。nRF52811 的 Code RAM 和 Data RAM 映射到同一块物理 RAM，代码加载后会占用数据 RAM，并不会得到额外内存。[Nordic nRF52811 产品规格中的内存说明](https://docs-be.nordicsemi.com/bundle/nRF52811-PS/raw/resource/enus/nRF52811_PS_v1.0.pdf)。

当前应用只有 6,816 B 未分配 RAM，栈预留为 2,048 B。加载器、重定位或固定链接地址、函数依赖、镜像版本/完整性、复位重载和调用期间禁止擦写都需要设计。如果还在内部保留同一代码的加载镜像，就没有减少内置 Flash；常规 RAM 函数声明本身并不能完成外置代码迁移。

因此不推荐当前项目走运行时代码装载路线。若长期业务代码仍超过扩大后的内置分区，应评估更大内置 Flash 的 MCU，或具有 XIP 能力的硬件方案。

## 3. 外置存储的实际约束

FM25Q04B 容量为 **512 KiB**，当前 FST3 采用：

| 区域 | 地址范围（不含末地址） | 容量 |
| --- | --- | ---: |
| 主目录扇区 | `0x00000–0x01000` | 4 KiB |
| 字体更新分配区 | `0x01000–0x7F000` | 504 KiB |
| 备份目录扇区 | `0x7F000–0x80000` | 4 KiB |

字体更新器会在整个中间区寻找尾部空间和可回收空洞，所以**当前未写入的数据区不是为其他模块保留的分区**。实际已安装字体大小需要读取设备，不能由代码容量宏推断。

可以评估以下最小布局，保持主备字体目录的位置：

| 区域 | 候选地址范围 | 容量 |
| --- | --- | ---: |
| 主字体目录 | `0x00000–0x01000` | 4 KiB |
| 字体更新分配区 | `0x01000–0x7D000` | 496 KiB |
| 配置/标注日志 A | `0x7D000–0x7E000` | 4 KiB |
| 配置/标注日志 B | `0x7E000–0x7F000` | 4 KiB |
| 备份字体目录 | `0x7F000–0x80000` | 4 KiB |

这是候选设计，尚未实施。缩区前必须检查旧 FST2/FST3 的有效字体记录是否落在新保留区，若有则先迁移并原子提交新目录；还要保证旧字体和新字体更新暂存空间均可满足需求。不能直接擦除尾部两个扇区。

需要同步调整：

- `EPD/font_store.h` 的字体容量边界，以及 `font_store.c` 的旧格式读取、区域校验和更新分配。
- `tools/font_store_tool.py` 的 `DATA_CAPACITY` 与导出/解析校验。
- `html/js/font_store.js` 的最大包容量判断；建议设备返回容量/布局版本，避免只依赖固件版本推测。
- 外置存储访问、唤醒和休眠的协调：字体提交/擦写与配置保存必须串行，不能出现一个任务将芯片休眠、另一个任务仍在读写。

外置 Flash 的 SPI1 引脚在 `fm25q04b.c` 中固定为 CS12/MISO13/SCK14/MOSI15，不依赖待迁出的 EPD 引脚配置，这有利于提前初始化并读取配置；但现有启动顺序仍需调整。外置读取失败时，应能使用板级默认值启动 BLE，提供重新配置/恢复入口。

## 4. 回收内置 8 KiB 的步骤

1. **先在旧 56 KiB 应用范围内实现过渡固件。** 完成外置分区兼容、两类数据迁移、CRC/提交确认；掉电后能继续识别有效副本。迁移相关双套读取代码也必须装得进当前分区。
2. **验证存储生命周期。** 字体更新、标注更新、配置保存、复位、掉电、空白外置 Flash、损坏记录都不能破坏另一类数据；迁移完成状态必须可持久化确认。
3. **处理 Bootloader 上限。** 当前 DFU 配置 `NRF_DFU_APP_DATA_AREA_SIZE=8192`；SDK 定义 `DFU_REGION_END = bootloader_start − app_data_area_size`。按当前 `0x29000` Bootloader 起点，旧配置仍限制在 `0x27000`。仅修改应用链接脚本，OTA 仍可能拒绝更大的镜像。
4. **核实并升级实际使用的 Bootloader。** 使用已验证支持新应用边界的 Bootloader，再生成扩大到 `[0x19000, 0x29000)` 的应用，容量变为 64 KiB。检查设置页、镜像校验、安装流程及升级失败恢复。仓库源码配置与现用预编译 HEX 的一致性必须确认。
5. **明确回退兼容性。** 较旧固件的字体分配器可能覆盖新增日志区；旧应用也依赖已被复用的 FDS 区。回退方案必须识别新的存储布局，不能继续把任意旧固件视为可直接回退。

若代码体积暂时保持 52,716 B，64 KiB 应用区将剩余 **12,820 B**。实际结果应为：

`新余量 = 4,628 + 8,192 + 删除的内置代码 − 新增的外置存储代码`

迁移兼容代码、Bootloader 更新和后续代码裁剪可能处于不同版本阶段，不能将所有理论收益在一个版本中重复累计。

## 5. 建议执行顺序

1. **当前版本：** 保留已实现的 4 KiB 预警，针对主程序/命令、GUI、字体协议寻找可验证的重复代码；不再做收益只有十几字节的盲目内联实验。
2. **预计新增功能会吃掉余量：** 建立专用内置日志原型，测量净体积与掉电恢复成本，再决定是否替换 FDS。
3. **明确需要增加约 8 KiB 应用容量：** 实施配置 + 标注完整外置迁移，连同字体分配器、工具、启动与 Bootloader 一起升级。
4. **需要多年日历在线更新：** 单独引入外置日历资源包，按可维护性评估，不承诺当前小表能带来显著净节省。
5. **业务执行代码长期超出 64 KiB：** 转向更大容量 MCU 或 XIP 硬件；不优先让现有 24 KiB RAM 承担动态代码装载。
