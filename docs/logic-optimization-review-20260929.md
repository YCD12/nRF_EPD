# 当前逻辑复核与下一轮优化顺序（2026-09-29）

本次复核以应用 BIN **49,112 B**、静态 RAM **5,308 B** 的当前实现为基线。仅新增评估和 `output/review-next-20260929/` 下的临时主机探针，没有修改固件或网页实现。结论：现有内置 Flash 执行代码、外置 Flash 存资源的架构可以继续使用；下一轮应先修正命令确认和配置应用的一致性，再优化重复读取与控制流。

## 优先处理的逻辑缺口

### 1. 通知队列满可能触发错误复位

位置：`EPD/EPD_service.c:1571` 的 CCCD 通知启用分支。

该分支调用 `ble_epd_string_send()` 发送配置，只豁免 `NRF_ERROR_INVALID_STATE`，其余结果交给 `APP_ERROR_CHECK`。当前发送函数采用非阻塞方式，发送队列满会返回 `NRF_ERROR_RESOURCES`。例如通知尚未排空时对端再次启用 CCCD，这种可重试的忙状态会进入 fatal 处理；发布配置的 SDK 错误处理最终复位。

建议：把需要可靠交付的首次配置通知变成待发送状态，在主循环或 TX 完成后重试，并在断连、关闭通知时取消；不要在 BLE 回调里忙等，也不要仅忽略错误而让网页永久拿不到初始配置。MTU/电压等信息可按重要性统一调度。

验证：用真实 `on_write()` 覆盖发送队列满、再次启用、TX 完成、关闭通知和断连。目前初始化/通知测试覆盖底层发送函数，尚未覆盖这个调用者的错误处理。

### 2. 连续切模式可能静默丢失后一次操作

位置：`EPD/EPD_service.c:1544` 的队列提交、`EPD/epd_command_queue.h:28`、`html/js/main.js:355`。

普通命令队列只有两槽。长刷新在主循环执行期间，BLE 中断仍能接收命令；一组 `SYNC_TIME_SILENT + SET_MODE` 就能占满两槽。第二组到达时，`epd_cmd_queue_push()` 返回 false，但入口既不回报失败，也不保留最新模式。网页只串行化单次 GATT 写入，没有等待整组模式操作被 MCU 接受；GATT 写成功后就提示模式已启用。此时设备最终可能仍执行前一次模式。

主机探针提取真实 `epd_service_on_write()`，在不消费队列期间依次发送“校时、模式 2、校时、模式 3”，确认最后仅保留第一组，模式 3 被丢弃。探针没有模拟真实 BLE 无线时序，触发链由中断分发配置及前端调用流程共同支持。

建议：模式选择可以合并为“最新待应用目标”，由主循环一次应用并安排刷新；有严格顺序要求的普通命令继续排队。需要可靠确认的操作应增加应用层接受/忙状态，并让网页整组串行或等待确认。单纯扩大队列只推迟问题并增加 RAM。

### 3. 整包配置的校验、保存与硬件应用不一致

位置：`EPD/EPD_service.c:1207` 的 `cmd_set_config()`，对照资源激活路径 `EPD/EPD_service.c:1437`、启动路径 `EPD/EPD_service.c:1753`。

`SET_CONFIG` 合并载荷后只校验 GPIO 编号，就更新 RAM 和外置记录并触发全刷。它没有校验 `display_mode` 和 `week_start`；合法引脚配上非法模式可以保存，且启动入口也只检查空配置/引脚。改变 GPIO 或型号时，它还没有重新加载 GPIO 或清除旧 `p_epd->epd`，会出现“已保存配置”和当前硬件状态不一致。常用网页的 `SET_PINS + INIT` 不等于这个整包协议入口已正确处理。

建议：建立共用的配置校验及应用路径，覆盖启动、整包命令和资源热重载；明确字段范围及默认型号语义。只有硬件相关字段改变才安全释放旧引用、加载新配置并重建驱动；只改周起始日等字段不需要重新初始化硬件。应用必须在主循环处理。

验证：非法模式/周起始日不落盘；修改引脚后实际 SPI/GPIO 与配置一致；修改型号失效旧驱动；只改显示配置不增加硬件初始化；重启恢复与资源热重载采用一致规则。

### 4. 合法自定义 UI 可能被错误分页裁剪

位置：`GUI/GUI.c:844`、`GUI/GUI.c:898`，对照 `GUI/ui_resources.c:36` 的组件校验。

全屏时钟头部的绘制范围截止于顶部横线，而不是由文字实际坐标决定。探针将头部 `y=100, value0=122`，保持默认横线 `y=68,h=1`；生产 UI 校验接受该包，但渲染器仍只在截止 70 像素的页面调用头部绘制，所以移位后的文字会漏绘。底部第二行 `value0` 与 `y+h` 之间也缺少一致约束。默认布局金图不会暴露这一问题。

建议：根据各行实际基线和字体 ascent/descent 求联合绘制范围，横线独立裁剪；同时核对分屏的范围。随后可以给日历头部和星期栏补正确的分页裁剪，减少无关页面上的文字解码和宽度计算。

验证：默认金图保持一致；新增头部、底部移位和跨页文字用例；校验允许的布局应与分页绘制结果一致。

## 可以继续优化的热点

| 顺序 | 候选 | 实际证据及收益方向 | 必须保留的边界 |
| --- | --- | --- | --- |
| 1 | 资源读取缓存未命中后回填 | `resource_store_read():176` 只在 `open()` 时建立单项缓存，miss 后不回填。资源加载最后打开 UI；UI 随后从 RAM 取组件，字体走物理区域读取，日历却反复走 miss。默认 8 项分区表探针实测：CAL 打开后一次读取仅 1 次 Flash 读；打开 UI 后，两次连续 CAL 读取分别都是 **7 次**。回填现有缓存可避免连续读取反复查表，无需新增常驻 RAM | 元数据缓存不代表完成整包 CRC；不能让 `open()` 跳过校验。mount、BEGIN、abort、commit、分区重定位均要失效，尤其分区表 BEGIN 的特殊分支 |
| 2 | CRC 扫描共用实现 | `resource_store.c:37` 与 `font_store.c:62` 各有分块读 Flash、累计 CRC 的循环，是 Flash 精简候选 | 当前块长 64/251 B、返回语义及喂狗方式不同；合并要同时核对栈峰值、SPI 次数和错误传播。整包 CRC 与字体槽 CRC 检查均保留 |
| 3 | 集中命令尾部喂狗 | `epd_execute_command():1275/1299` 已在命令前后喂狗，多数 `cmd_*` 返回前又喂一次，队列 worker 在 `:1336` 再喂一次。可删除返回前紧邻调用者喂狗的重复点 | 驱动 BUSY 等待、Flash 操作和长绘制内部的喂狗保留；只有静态调用关系明确的尾调用才合并 |
| 4 | 减少一次激活中的重复挂载和包头定位 | `epd_resources_reload():19` 挂载后，字体/日历/UI 初始化又分别挂载；字体路径还依次 find/info/open 同一资源 | 区分一次激活内复用已校验上下文与写入前重新校验。保留冷启动初始化顺序、维修会话和写入前 mount；不要简单删除全部 mount |
| 5 | 减少每页重复的月历派生计算 | `GUI.c:465` 中同一天在相交页重新计算农历并扫描节日/假日；`calendar_resources.c:119/140` 逐条读取记录。日历头部/星期栏还会在每页重新绘制 | 先修正裁剪并测资源缓存回填的效果，再考虑小型行缓存；不默认增加整月或整屏缓存。主要收益是读次数和耗时，可能增加 RAM/BIN |

前三项适合小步实现并独立 A/B。本次只验证当前行为，没有编译优化版本，不能把函数大小、Flash 读次数或源码删行数换算成尚未测量的 BIN 节省值。

## 可读性整理与不宜直接删除的代码

- `main.c` 启动末尾的看门狗/其他复位分支都调用同一个强制刷新函数，可将日志条件与刷新调用分开；发布日志已关闭时，编译器通常已消除重复，主要是可读性收益。
- 当前网页连接门槛为 `0x37`，`main.js` 仍有针对 `<0x21`、`<0x34` 的成功连接后旧固件分支，可在完成浏览器回归后清理；这只减少网页复杂度，不节省 MCU Flash。
- 命令接收与执行阶段的资源互斥检查不能仅因重复就删除：命令等待队列期间，资源会话状态可能改变。
- GPIO 引用计数、连接代次、通知排空状态服务于不同的中断/主循环及生命周期边界，不应为减少几个字段直接合并。
- 不调整单张图片直接写屏幕 RAM、连接中刷新、断连后间歇广播；不删除资源 CRC、缺资源提示或冷启动恢复。

建议实施顺序：**通知背压处理 → 模式操作确认与合并 → 配置统一校验/应用 → UI 裁剪正确性 → 资源缓存回填 → CRC/尾部喂狗 A/B → 挂载及分页计算优化**。正确性修复可能略增代码，应与体积精简分开记录。三个临时探针均运行通过；本轮没有硬件实测，也没有因只读 review 重跑整套发布构建。
