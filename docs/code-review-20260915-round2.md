# 第二轮代码审查：功能、结构与内置 Flash

> 实施状态：本报告列出的四项问题及后续结构／Flash 优化均已处理；最终结果见 `docs/code-optimization-20260915-round2.md`。以下内容保留为修改前的审查依据。

审查对象是上一轮优化后的工作区，应用 Flash 为 53,136 字节，静态 RAM 为 6,800 字节。本轮保留现有业务源码和暂存区，只新增本报告及 `output/review2/` 中的隔离实验。实验镜像不是待发布固件。

## 功能问题（按优先级）

### 1. P1：GPIO／SPI 生命周期存在引用泄漏

位置：`EPD/EPD_service.c:599`、`:616`；`EPD/EPD_driver.c:95`、`:148`。

`on_connect()` 无条件调用 `EPD_GPIO_Init()` 增加引用；`on_disconnect()` 只有在 `p_epd->epd != NULL` 时才释放。设备处于时钟休眠状态时该指针可为空，连接后只读配置再断开，就会留下连接持有的引用。刷新中断开也直接返回，而刷新收尾只释放本次刷新获得的引用。多次连接后可能使 SPI／GPIO 长期不释放，影响待机功耗和重新配置引脚。

此外 `EPD_GPIO_Uninit()` 对无符号计数直接 `--`，没有零值保护。整理生命周期时应一并防止重复释放下溢。

建议明确连接与显示操作各自的资源所有权。连接本身尽量不打开显示总线；需要绘图／传图时获取，完成或取消时对称释放。若保留连接持有资源，则必须在所有断开路径安排主循环释放，不能依赖屏幕描述指针是否为空判断是否持有资源。

### 2. P1：标注回读不能在通知队列满后续发

位置：`EPD/EPD_service.c:971`、`:1501`；`html/js/calendar_annotations.js:353`。

`cmd_send_annotations()` 在局部变量中保存 offset，用循环发送整个 blob，任一次通知失败便退出。`HVN_TX_COMPLETE` 只唤醒字体任务，标注没有保留发送位置或恢复任务。SDK 默认通知队列容量为 1，本项目未设置 `hvn_tx_queue_size`；因此不能依靠连续调用发送接口完成多片回读。

本轮直接提取原函数并模拟一个可用通知槽：48 字节标注、20 字节通知载荷，只成功发送 15 字节数据，第二次提交失败后函数返回。前端只等待 4 秒，没有自动从缺失位置继续，最终报告回读失败。默认 244 字节载荷下，较多标注同样需要多片通知。

建议提取小型 BLE 通知发送状态机，保留操作类型与 offset，收到 TX_COMPLETE 后继续。复用字体已有的等待／重试约定，避免另建一套阻塞循环。发送期间还需保证回读数据版本一致。

### 3. P2：标注上传中断后，已保存标注不会自动恢复

位置：`GUI/calendar_annotations.c:271`、`:222`；`EPD/EPD_service.c:616`。

首片上传设置 `m_rx_active`，清空 live 缓冲并使 `m_live_len = 0`。错误分片可以触发 `restore_live()`，但如果后续分片永远不来，断开和定时器路径均未触发恢复。此时查询数量为 0、GET 取不到 blob，日历也不显示旧标注，直到重启、重新完整上传或主动清除等操作改变状态。

本轮重现了首片之后 `count == 0`、`blob == NULL` 的状态；持久化 Flash 内容本身未因此被删除。

建议增加接收取消接口，在断开／超时后由主循环恢复最近已保存版本。保存接受、传输完成、FDS 持久化完成应明确区分，前端回读 live 数据成功不能作为已经落盘的证明。

接收复用 live 缓冲还需要进一步覆盖中断交错：绘图在主循环查找标注，BLE 中断可能清空并改写同一缓冲。`m_rx_active` 的一次检查不能保护整个查找和复制过程。应对一次记录读取提供一致性保护，并明确整帧遇到标注变更时的重绘策略。

### 4. P2：GUI 刷新请求仍可能因调度队列满而丢失

位置：`EPD/EPD_service.c:1739`、`:1803`、`:1825`。

字体延迟刷新先清除 `refresh_pending`，跨天判定先推进 `s_last_tick_day`，最终 GUI 入队没有处理失败。调度队列满时，时钟通常等下一分钟；纯日历则可能一直等到下一次跨天或手动操作，才更新日期或刚上传的字体。普通命令队列已经有主循环重试，但 GUI 刷新尚未统一使用这一模式。

建议收敛为 `display_request_refresh()`：保存最新时间和强制全刷原因，合并重复请求，只有成功入队／执行后才消费；队列满时保留 pending，由主循环重试。这也能收敛标注、字体、模式切换、校时、电量恢复的重复调度代码。

## 内置 Flash：实测能继续降低，但幅度需要如实看待

重新构建当前源码确认基线，随后只在源码副本中做裁剪实验。工具链为仓库 ARM GCC 9.3.1，使用相同发布配置、链接脚本及 `-Os -flto`。

| 隔离实验 | 应用 Flash（字节） | 相对当前节省 |
| --- | ---: | ---: |
| 当前源码 | 53,136 | — |
| 将 GUI 布局尺寸固定为当前 800×480 | 52,624 | 512 |
| 字体绘制仅保留方向 0 | 53,040 | 96 |
| 合并以上两项 | 52,512 | **624（1.17%）** |

合并后应用 Flash 余量由 4,208 增至 4,832 字节，静态 RAM 保持 6,800 字节。LTO 会改变函数内联与布局，因此单项收益不能直接相加。

合并实验通过 30 组完整画面基准对比，以及局刷 OLD／NEW 每字节对比和错误回退测试。实验只验证当前屏型；正式实现应通过产品配置宏限定尺寸／文字方向，保留主机通用绘图能力，不能把实验中的常量替换直接推广到其他屏幕。

全局 `-fno-inline` 实验反而使应用超出 Flash 区 2,888 字节，不能作为省空间方案。关闭调试信息也不会减少烧录到芯片的代码；本工程已启用段回收和 LTO，删除没有被链接的函数／字体数据同样没有烧录体积收益。

当前较大的链接符号如下，包含 LTO 内联进来的其他函数，不能简单视作同名源码函数的独立成本：

| 链接符号 | 字节 |
| --- | ---: |
| `epd_gui_update` | 4,732 |
| `main` | 4,208 |
| `DrawMonthGrid` | 2,812 |
| `epd_execute_command` | 2,024 |
| `cmd_font_store` | 1,770 |

下一步值得实测的方向：

- 合并刷新请求与通知发送的重复控制逻辑；既补功能缺口，也减少维护分支。最终净 Flash 变化必须在修复完成后重新测量，不能预先计入 624 字节收益。
- 日期数字目前先经 `GFX_getUTF8Widthf("%d")` 格式化测宽，再经 `GFX_printf("%d")` 格式化绘制。可一次格式化后复用，并让“年／月／日”等固定文本统一走直接输出；这更确定地降低重复计算和栈使用，Flash 收益需要 A/B 构建。
- 将当前单屏型号选择、布局常量、字库槽位规格集中为产品配置，给编译器提供明确常量。不要仅删除驱动表：当前只有一个型号，LTO 已能消除相当一部分选择逻辑。
- 旧图片命令、旧字体数据格式迁移若仍被前端或已部署设备使用，应保留。只有明确终止兼容后才考虑裁剪并重新测量，不能把删除这些功能包装成无损优化。

不建议为节省代码去掉字库 CRC／边界校验、失败回退或异步存储保护；也不建议在本轮重写 FDS 或挪动应用／bootloader 分区。资源字库已存外置 Flash，继续删除 `fonts.c` 中被宏排除的字模不会降低当前固件体积。日历常量可以外置，但其收益有限，还会引入加载和校验路径。

## 源码结构：先划分职责，再移动目录

主要问题是 `EPD_service.c` 同时承担 BLE 接入、命令执行、图片传输、刷新、电量处理及标注读写；`GUI/GUI.c` 同时维护布局、节日数据和格式化；`GUI/fonts.c` 同时包含字模资源和直接依赖 `font_store` 的硬件适配。`GUI/GUI.c` 还包含未实际使用的 `EPD_driver.h`，增加主机测试对硬件头文件的依赖。

建议分两步整理：

1. **先在现有目录提取职责。** 从 service 中提取 `display_manager.c`、`image_transfer.c`、`ble_tx.c`；把数字命令 ID 放入纯数据 `epd_protocol.h`，服务、策略和测试共享，避免策略头重复硬编码。将 `storage_retry.h` 的实现从配置存储中移到独立 `fds_jobs.c`，让标注存储不再隐式依赖配置模块推进 GC。日期数据／日期计算与布局分开，外置字体适配从通用 GUI 中抽离。
2. **再按稳定边界移动目录。** 可分为 `app/`、`ble/`、`drivers/`、`storage/`、`gui/`、`boards/`；芯片／屏型／特性开关统一放到 board 配置。同步更新 GCC、Keil、主机测试和工具引用；不要只改 Makefile，留下 Keil 工程失效。

避免引入大量通用接口和回调表：当前产品只有一块屏，应优先小函数、明确状态和单向依赖。单纯把一个大文件拆成几个文件不保证减少 Flash；启用 LTO 时，整理前后通常应先要求行为与体积基本不变，再单独测优化收益。

## 验证与执行顺序

本轮重新完成当前源码 ARM 构建和完整主机测试：26 个 C 测试程序、13 个 Node 测试、3 个 Python 测试全部通过，日志为 `output/review2/host-tests.log`。合并裁剪副本另行完成绘图回归。现有测试通过不代表上述功能缺口已覆盖；尤其缺少服务级通知背压、断开时资源释放及 GUI 调度失败的集成用例。

标注通知背压和中断接收状态的最小复现位于 `output/review2/reproduce_annotations.c`，生成脚本保留原回读函数；Flash 实验脚本为 `output/review2/experiments.py`。未烧录硬件，GPIO 待机功耗影响尚需上板测量。

推荐顺序：修复 GPIO 生命周期和标注通知续发 → 补标注取消／超时及刷新请求重试 → 提取对应模块 → 正式加入两项屏型裁剪 → 重新报告最终 Flash／RAM 并验证 OTA。基于目前隔离实验，可以确认仍有至少一组节省 624 字节的候选方案；不能把这一数字直接当作包含全部可靠性修复后的最终净收益。
